## Idea Source
IDEAS.md — the first queued idea:
> **P2P encrypted screen share** — share your screen (or a single window/tab) to one or many viewers over the encrypted tunnel; getDisplayMedia → WebRTC + SFrame, no Zoom/login/extension. Great for quick "look at my screen" help sessions where you don't want a corporate account in the middle. Viewers can grab a local clip. Artefact: viewer room link + optional local screen recording.

Fleshed out into a broadcast tool: role choice (Present/Watch), a big presenter stage with a
thumbnail strip for multiple presenters, optional mic narration mixed into the share, and two
artefacts (local WebM recording + PNG snapshot). Per the trystero-p2p recipe, dropped the SFrame
per-frame layer the idea text mentions — it's redundant in a full mesh (every stream is already
direct DTLS-SRTP) and trystero doesn't expose per-sender encoded transforms. Shipped the honest,
verifiable E2E story instead: passphrase-encrypted signalling + full-mesh DTLS-SRTP + a four-word SAS.

## Expansion check
meetwell already has *optional screen share within a symmetric call*. Castwell is a distinct product:
a one-to-many **broadcast** (getDisplayMedia as the primary input, presenter-stage UX, viewer-side
recording of what you watch), with a different search intent ("share my screen without Zoom", "screen
share no download"). Built as a new tool, not an expansion.

## Tool Details
- **Name:** Castwell
- **Repo:** ben-gy/castwell
- **Category:** p2p-communication (privacy in the public index)
- **Audience:** anyone who says "let me just show you my screen" and doesn't want a corporate meeting
- **Stack:** Vite 6 + vanilla TypeScript + Vitest
- **Browser APIs:** Screen Capture (getDisplayMedia), WebRTC (full mesh via trystero/nostr), Web Crypto
  (PBKDF2/SHA-256 SAS), getUserMedia (narration), Web Audio (mixing + metering), MediaRecorder,
  Canvas 2D (snapshot), Screen Wake Lock, Web Share/Clipboard, Service Worker (PWA)
- **Worker strategy:** main-thread only — a live broadcast is event-driven, no CPU-bound work to offload

## Privacy Model
- **Protected:** screen + audio travel full-mesh browser-to-browser, DTLS-SRTP encrypted, no media
  server; the user picks exactly what to share in the browser's own picker; the passphrase encrypts
  the handshake and lives only in the link hash; nothing recorded unless the user presses Record/Snapshot.
- **Not protected:** public nostr relays learn an ephemeral room id (handshake encrypted); IP visible
  to peers + STUN; symmetric-NAT-with-no-relay may fail (no TURN relay by design); a viewer can record
  what you show them; anyone with the full link can join.
- **Trust surface:** static bundle + TLS; public relays + STUN (encrypted handshake only); Cloudflare
  Web Analytics beacon (anonymous page views); feedback widget (only on explicit Send).

## Architecture Decisions
- Reused the proven meetwell/talkwell P2P core near-verbatim: crypto (SAS), wordlist, room/router,
  eventlog, glossary, icons, modals shell. New `session.ts` controller is the broadcast variant of
  meetwell's call controller (addStream to all peers; setShareStream/stopShare).
- **Genuinely different recorder:** unlike meetwell's canvas grid-compositor, a screen broadcast is a
  single stream, so `StreamRecorder` hands the raw focused MediaStream straight to MediaRecorder at
  full resolution — no canvas, no re-encode. Records a *clone* of the stream so a presenter swapping
  windows doesn't kill an in-flight clip.
- **Audio mixing:** the outgoing share always carries one (possibly silent) mixed audio track
  (system/tab audio + mic summed via Web Audio MediaStreamDestination), so the mic can be toggled
  mid-share by connecting/disconnecting its source node — no WebRTC renegotiation.
- Distinct broadcast-blue accent (#38bdf8) to separate Castwell from meetwell's teal in the fleet.

## Production dry-run (two-tab P2P over real relays)

grant, so **no real live screen broadcast was verified in this pipeline.** What WAS verified end-to-end,
by joining the same room in two browser-pane tabs over the real nostr relays:
- both peers connected (peer discovery + WebRTC connect)
- both derived the **identical** four-word SAS ("cherry · bronze · rocket · acorn")
- viewer count showed 2 on both sides
