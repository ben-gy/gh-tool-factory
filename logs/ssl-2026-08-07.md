## The 08:10 pass repeated a known-harmful action

Yesterday's log ended with an explicit instruction for this morning:

> **Tomorrow's 08:10 run will cycle them unless something stops it** … Either pass
> `--max-cycles=0` again, or bump `--cooldown-hours` past the intended quiet period.

Nothing did. The routine's command line is fixed and a log file is not an input to anything,
so the run cycled `au-inflation`, `au-approvals`, `au-insolvency`, `metascrub`, `facet` and
`noisewell` — abandoning their authorizations for the second time in three days. Under the
leading hypothesis (abandoning an authorization taints the hostname it was opened against)
this is the exact loop that keeps them broken: cycle → abandon → taint → cycle again.

Re-checked immediately after: **not one of the seven states moved.** All still `new` or
`authorization_created` on unchanged hostnames.

That this happened is a defect in the routine, not an oversight to be remembered better —
recorded as **Cause 6** in `ssl-root-cause-analysis.md` and fixed in `fleet-ssl.mjs`, which
now carries durable holds. The seven are held until **2026-08-14**.

## Still outstanding for the operator

**1. `metascrub-app.benrichardson.dev` is still serving someone else's gambling spam.**
Unchanged since 08-06 — still 200, still their certificate, still renewing out of our
Let's Encrypt bucket. It is deliberately *not* auto-remediated: the standing guardrail only
permits deleting a record GitHub reports unclaimed, and this one is claimed — by them.
Deleting a record a third party is actively serving stays an operator decision. One call:

```bash
CF=$(cat ~/.claude/secrets/cf-benrichardson-token); ZID=bf71cf2904d22db3443bb471e5dbdde2
ID=$(curl -s -H "Authorization: Bearer $CF" \
  "https://api.cloudflare.com/client/v4/zones/$ZID/dns_records?name=metascrub-app.benrichardson.dev" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["result"][0]["id"])')
curl -s -X DELETE -H "Authorization: Bearer $CF" \
  "https://api.cloudflare.com/client/v4/zones/$ZID/dns_records/$ID"
```

**2. `kiln.benrichardson.dev` is a property in no registry.** Repo `ben-gy/kiln`, created
2026-08-06, Pages `cname` set, certificate `approved`, serving 200. It is healthy, but no
registry lists it, so the sweep does not monitor it and no index links to it — the inverse
of Cause 3 registry drift: reality the registry does not know about. It surfaced only
because the new zone-sweep prune had to decide whether its record was an orphan (it
correctly declined, on both the 48h grace window and the unclaimed test). Worth deciding
whether it belongs in the tool registry or was an abandoned experiment.
