## Architecture Decisions

**Toolchain bumped off the fleet default, on purpose.** The fleet ships vite ^6 / vitest ^2 /
vite-plugin-pwa ^0.21, which reports 5 npm advisories (one critical, one high — all dev-server only:
the esbuild dev server, vite's `fs.deny` bypass, the vitest UI server). None affect the shipped
static bundle, and the design spec explicitly recommended staying on the fleet trio. I bumped to
vite ^7.1.13 / vitest ^3.2.6 / vite-plugin-pwa ^1.0.3 anyway and it reports **0 vulnerabilities**.
The reasoning: this is a *security* tool, and a security engineer evaluating it will run `npm audit`
on the repo before they run the tool. The risk (an untested plugin config surface) was retired
immediately by building and testing on the new trio before writing feature code.

**Two spans per finding.** `matchStart/matchEnd` for overlap resolution, `redactStart/redactEnd` for
the actual replacement, as separate required fields so there is no single `{start,end}` to get
wrong. They differ on five rules. The worst case this prevents: a `pem-private-key` rule that matches
only `-----BEGIN EC PRIVATE KEY-----` would redact 30 characters and leave the whole key body in the
file the tool calls clean. A test asserts that span exceeds 78 characters, and a second rule catches
truncated blocks at the same severity.

**Byte splicing, never JSON round-tripping.** Verified during design: `JSON.parse` →
`JSON.stringify` turns `12345678901234567890` into `…67000`, `1.0` into `1`, `1e5` into `100000`,
and collapses duplicate keys; `TextDecoder` defaults to `fatal:false` and substitutes U+FFFD, so 16
bytes of invalid UTF-8 become 24 different bytes. Both are disqualifying for a file destined for a
fine-tune. Detection decodes a copy; the splice works on the original bytes, and
`spliceBytes(raw, [])` returns the same object.

**fflate over `DecompressionStream` for gzip input**, at a measured 2.26× cost. `cat shard-00.gz
shard-01.gz` is routine in sharded ML pipelines and produces legal multi-member gzip; browser
behaviour on it is unverified; and the obvious sanity check, the gzip ISIZE trailer, is *unsound* on
multi-member input — with equal-sized shards a truncated read passes. Silently scanning half a file
and reporting "clean" is the worst thing this tool could do.

**Counted credits, not recycled buffers.** The textbook design hands the `ArrayBuffer` back as the
credit; that collides with pass 2, where the splicer returns the *same* buffer when a chunk is clean,
so it cannot simultaneously be the output and the credit. A counted credit gives identical
backpressure with none of the aliasing hazard. No `SharedArrayBuffer`, hence no COOP/COEP, hence it
runs on GitHub Pages unmodified.

**The entropy gate was redesigned after measurement.** The specified `H ≥ 3.5 bits/char over 20+
chars` is wrong in both directions: English prose scores 4.53, a git SHA 3.91, and uniform random
20-char hex averages **3.36** — so it flags sentences and misses secrets. Maximum entropy at length
L is log2(L), so a constant bits/char threshold is length-coupled by construction. Shipped instead:
length-normalised `η = H / log2(alphabet)` at 0.92, behind an unbounded candidate tokeniser, ten
structural suppressors and a two-character-class requirement. Still off by default.

**Scope cut, and stated:** no GLiNER (192 MB, out of reach on a 4 GB phone → no names, no
addresses), no zstd (refused by name), no Parquet writer, no OPFS write branch, no resume, and no
corpus-frequency entropy suppressor (it would force a third pass).

## Errors & Resolutions

**1. A deadlock that hung every run at 100% — caught by the browser, invisible to unit tests.**
`maybeFinish()` did `writeChain = writeChain.then(async () => { …; await writeChain; })`, awaiting
the very promise it was constructing. The reader reported the full file read and then nothing ever
resolved. Replaced with a standalone `finalize()` that awaits the chain, pushes the gzip tail, and
re-reads the chain *after* the push. This is the single strongest argument for the Step-11 dry-run
existing at all.

**2. The `.gz` sample was silently decompressed by the host.** A static server sends a `.gz` asset
with `Content-Encoding: gzip`, so `fetch()` transparently inflated it — the demo handed back 1 MB of
plain JSONL inside a `File` named `.jsonl.gz`. The magic-byte sniffer saw through it correctly (it
reported "plain text"), but the filename was a lie and the demo would never have exercised the gzip
reader. The sample now ships plain, and the gzip path is verified separately with a
`CompressionStream`-built file.

**3. GitHub push protection rejected the first push.** Anticipated and mitigated in advance — the
sample is generated at `prebuild` and gitignored, and credential prefixes in fixtures are split with
`+` so no source file holds a contiguous token — but one slipped through: the Mailchimp fixture,
32 hex characters plus `-us14`, which has no checksum to deliberately break. Split it, amended, and
the push succeeded. **Lesson for the fleet: a scanner-fixture tool must assume its own fixtures are
detectable, and the split-prefix discipline has to cover shapes with no checksum too.**

**4. Rule counts drifted in prose.** The How-it-works copy hardcoded "Twenty-six recognisers … four
… eighteen …" while the registry had grown to 29/27/19. Replaced the numbers with `data-count`
spans filled from `COUNTS` at render time, so the prose can no longer drift from the registry.

**5. Stale service worker served an old bundle twice** during the dry-run (the known fleet trap).
Unregistered + cleared caches before each re-verification.

**6. Control characters emitted literally into a CSS-adjacent regex.** Writing a
`[\x00-\x1f]` character class produced real control bytes in `csv.ts`. Replaced with an explicit
charCode loop, so no source file contains control bytes at all.

## Deviations from the design spec

The spec was produced by a 13-agent workflow (6 research lenses, each adversarially refuted, then
synthesised). Three of its recommendations were **not** followed, each deliberately:

- **Toolchain:** it recommended downgrading to the fleet's vite ^6 / vitest ^2. I kept vite 7 /
  vitest 3 to clear all npm advisories — see Architecture Decisions.
- **The feedback widget:** it recommended dropping it entirely, on the grounds that a free-text box
  a user could paste a live secret into, on an origin granted script execution in a document holding
  plaintext secrets, is a bad trade. The factory's widget requirement is non-optional, so it ships —
  with the origin named in the Privacy modal and an explicit *"Do not paste a real secret into it."*
- **Precaching the sample:** it wanted `gz` removed from `globPatterns` so planted tokens are not
  written to every installed device. Moot now that the sample is plain `.jsonl` — but `jsonl` **is**
  in `globPatterns`, because the factory requires the sample to work offline. The planted tokens are
  synthetic and carry the literal `SCRUBJAYsample`.

## Honest gaps

- **No real multi-gigabyte test.** Everything verified above ran against a 1 MB sample. The
  streaming design is sound and resident memory is bounded by construction, but nobody has put 4 GB
  through it, and the throughput figures in the spec were measured in Node/V8, not in a browser
  worker — which is why the UI shows a live-measured *range* and never a predicted number.
- **No real-device mobile test.** The 375px checks are a resized desktop browser.
- The in-app Browser pane reports a 0×0 viewport until `resize_window` is called; before that,
  `elementFromPoint` returns null and the overlay-blocking check is vacuous. Worth remembering for
  future runs — resize first, then run the escape-hatch test.
