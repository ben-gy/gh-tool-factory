## What the preflight changed before a line was written

23 agents, ~2.45M tokens, every load-bearing claim attacked by an independent
refuter. **The spec was wrong in five places and the shipped tool repeats none
of them.**

1. **"The two towers must run in separate workers with separate ORT
   environments."** Refuted against the official `Xenova/webgpu-mobileclip`
   Space, which runs both in one context. Both towers ship in one worker.
2. **"`vision_model_quantized.onnx` (11.8 MB)."** That file is numerically
   destroyed. Measured here over 8 photographs × 8 queries against fp32:

   | vision dtype | cosine vs fp32 | top-1 ranking agreement |
   |---|---|---|
   | fp16 | mean 0.99999, min 0.99996 | **8/8** |
   | int8 | mean 0.25297, min 0.12997 | **0/8** |

   It loads without error and returns well-formed 512-d vectors, so nothing
   about the failure is visible from outside. This reproduces loraprep's finding
   and **contradicts a preflight agent that called int8 safe on a 3-image
   probe** — the probe was too small to see it.
3. **"`max_length: 77` is required."** `padding: 'max_length'` is the mandatory
   part; 77 comes from `tokenizer_config.json`, and passing 32 throws.
4. **"Mean/std normalisation."** `do_normalize` is false — 256×256, rescale by
   1/255 only. (So `CanvasSink fit:'cover'` at 256 IS the model's preprocessing.)
5. **"red car turning left" / "someone at the front door" as the demo queries.**
   CLIP has no temporal modelling; verb phrases collapse to their nouns. The
   whole product was rescoped to noun-phrase scene queries and the interface
   says so in three places.

**One adversarial agent recommended abandoning the idea outright** ("killed on
physics"), on four grounds. Two were adopted (no verb phrases; never present a
bare ranked list). Two were refuted by measurement — its cost analysis was for
ViT-L/336 at ~300 MB, not the 68 MB MobileCLIP-S0 actually used, and its central
claim that dashcam footage is too homogeneous was tested by a refuter on **262
frames of real 4K forward dashcam footage** (Wikimedia Commons, CC BY), which
found the top-10 mean 13.6–71.5% above the median cosine (z = 1.27–3.32) with
top-1 visually correct on 5 of 5. That measured range is what calibrates the
"stands out" figure the interface prints.

Also found: a free, hosted, client-side CLIP video-search page already exists
(`tobidi0410.github.io/ai-video-search`, 1 star, invisible in every SERP) — it
ships **no export at all**, which is why the clips/VTT/CSV/index are the
headline here and the search is not.

## Privacy Model

- **Protected:** the video, every frame, every thumbnail, every clip, and every
  query. No upload API and no storage API in first-party code; the build gate
  asserts it against `dist/`.
- **Not protected:** the one-off model fetch is visible to Hugging Face (it says
  nothing about the video); the page load is visible to GitHub Pages and
  Cloudflare; an exported clip is an ordinary file.
- **Trust surface:** this bundle, `huggingface.co` + its Xet CDN once, the
  cookie-less Cloudflare beacon, and feedback.benrichardson.dev only on Send.
  The gate parses the shipped CSP and fails on any `connect-src` origin the
  privacy modal does not disclose.

## Architecture Decisions

- **Keyframes are enumerated without decoding** (`getFirstKeyPacket` →
  `getNextKeyPacket`, `metadataOnly: true`), so a multi-GB file yields a real
  frame count and a real estimate before the user commits. Verified: 43
  keyframes at exactly the 2.0 s GOP on the demo reel, in under a second.
- **The sampling ladder goes both ways** — thin dense keyframes, interpolate
  across long GOPs.
- **Backpressure is mandatory:** hardware decode far outruns single-threaded
  inference, and at 262,144 bytes a frame a three-hour file would queue ~2.8 GB.
- **Rank, never threshold**, with a robust z-score (median + MAD, falling back
  to standard deviation when >half the frames tie, which is what a locked-off
  camera produces) and the distribution drawn beside every result.

## Test Results

- **Tests written: 70. Passed: 70. Failed: 0.**
- Five failed on first run and **three were real engine defects**, fixed rather
  than re-baselined:
  - `standout` returned 0 when >half the frames tie — MAD is zero there, which
    is exactly the locked-off-camera case. Now falls back to the standard
    deviation (which can only understate a find, never invent one).
  - `findMoments` used the **median** as the background level, so a query
    matching more than half the video put the baseline inside the event and one
    11-second event came back as **four** overlapping results. Now p25.
  - The extent walk was bounded by the merge gap, which is a statement about how
    far apart two results must be and says nothing about how long one lasts.

  panel with frame count, download size and tier-aware estimate.
- Model download of exactly the intended files (`transformers-cache` held

- **Model ready on WebGPU with both self-checks passing: image 0.9997, text
  0.9922** against the committed reference vectors.
- Frame scanning to 74 of 83 with live rate and ETA.
- **The modal dismissal contract on all five overlays** — × (measured 44×44),
  backdrop `pointerdown` as a real touch sequence, Escape, no double-fire
  reopen, inside-panel pointerdown does not close, `body` overflow restored, and
  no `[hidden]` element rendering.
- Stylesheet loaded, dark palette applied, footer + feedback widget present.

**NOT verified, stated plainly:**
- **The query → moments → thumbnail → clip-export chain was never driven end to
  end in a browser.** The machine sat at **load average 45** on 12 cores with
  concurrent factory runs, and the preview browser could not complete ONNX
  session creation on repeated attempts — on WebGPU (after one earlier success)
  or WebAssembly, at either dtype. Scoring, smoothing, suppression and ranking
  ARE covered by `scripts/measure-retrieval.mjs` end to end (8/9 top-1 correct
  over the shipped reel) and by the unit suite; the **clip export and the
  thumbnail path are covered only by unit tests and code review.**
- **No WebGPU throughput figure is quoted anywhere**, because none was measured
  cleanly. The interface says the real speed is measured a few seconds into the
  scan, and quotes a firm number only for the WebAssembly tier.

## Errors & Resolutions

| Problem | Resolution |
|---|---|
| Preview served **peelback's** cached shell on :5199 | Known fleet trap; unregistered the SW and cleared caches. |
| Gate failed on `XMLHttpRequest` in the worker chunk | It is Emscripten's `open("GET",…)`/`send(null)` loader. Rather than exempt it, the gate now asserts **every `open()` in a worker chunk uses GET or HEAD** — stricter than the ban it replaced. |
| Gate failed on missing `third-party-notices.txt` | `make-notices.mjs` runs after `vite build` (it reads the shipped source maps), so it now also writes into `dist/` — otherwise the notices ship one build stale. |
| Scan hung at "Getting the model ready…" | `'gpu' in navigator` is not enough: `requestAdapter()` can hang and session creation inherits it. Added an adapter deadline, a session deadline, and a documented `?backend=wasm\|webgpu` escape hatch. |
| Scan stalled at 74/83 frames | The slow-session watchdog fires on ordinary variance (its baseline is the fastest frame ever seen) and re-ran device selection mid-scan. **Removed.** |
| A per-frame failure never returned its decode credit | An error now also cancels the decoder, so a visible error is not also a silent stall. |
| `Conversion` can discard tracks | `isValid`/`discardedTracks` are checked before `execute()`, with a plain-language message. Found by attempting the export in Node. |
| An earlier comment claimed "fp16 hangs on the WASM backend" | **Not established** — fp32 failed identically in the same browser, so that was evidence about the environment. Corrected in `config.mjs`; the fp32-on-WASM choice now rests on the measured speed difference (949 ms vs 1,156 ms per image) instead. |
