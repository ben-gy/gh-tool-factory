## Tool Details

- **Name:** docxray
- **Repo:** ben-gy/docxray
- **Category:** documents
- **Audience:** a professional about to email a contract, board pack or HR file outside their
  organisation — lawyers, accountants, HR, procurement, grants, academia.
- **Stack:** Vite 7 + vanilla TypeScript. One runtime dependency (`fflate`).
- **Browser APIs:** fflate over the OPC ZIP, a first-party XML reader in a module Web Worker,
  `createImageBitmap` + Canvas 2D for the crop reveal, `canvas.toDataURL` for the export,
  Web Share where available, Service Worker for offline.
- **Worker strategy:** one dedicated module worker doing unzip, parse and every walk; image
  bytes transferred back rather than copied.

## Privacy Model

- **Protected:** the document is unzipped, parsed and rendered in the tab; **zero network
  requests while it works** (verified in the browser — see below); nothing written to disk;
  the file is opened read-only and there is no code path that writes a `.docx`.
- **Not protected:** the exported report contains the revealed content by design and is as
  sensitive as its source; the feedback form on an explicit Send.
- **Trust surface:** the static bundle on GitHub Pages, the Cloudflare Web Analytics beacon,
  `feedback.benrichardson.dev`. Nothing else — no model, no CDN asset, no remote data.

## Architecture Decisions

**The XML reader is first-party, and that was forced rather than chosen.** `DOMParser` is
declared `[Exposed=Window]` in the HTML Standard, so it does not exist in a dedicated worker in
any engine — confirmed both normatively and empirically during review. `IDEAS.md` specified
`DOMParser`; it is wrong. Parsing a 300-page board pack on the main thread would freeze the tab
exactly while the progress bar should be moving.

**Everything resolves by namespace URI, never by prefix.** `w:` is a convention, not a name.

**The container layer was shaped by measurement, not habit.** `unzipSync` over a 60 MiB package
costs ~67 MiB of extra heap; the same call *filtered* to XML/`.rels` costs a few hundred KB.
Streaming measured **slower** (39 ms vs 32 ms) because the file is already an `ArrayBuffer`
before fflate sees it, so only the filter saves anything. Media is extracted one entry at a
time and only for pictures that carry a crop.

**Strictly read-only.** Emitting a cleaned `.docx` means owning `[Content_Types].xml`, every
`_rels` part and every relationship; one mistake is a Word repair dialog on somebody's
contract, which is worse than the disclosure. A build gate asserts `zipSync` never reaches the
bundle, so the promise is structural rather than a claim.

## Adversarial Review — what it changed

Four investigations and four independent refutations (9 agents, ~990k subagent tokens). The
architect synthesis agent died on an API connection error; its inputs were all present, so the
design was carried out directly from the investigations and refutations rather than re-run.

1. **The product pitch was false and was rewritten.** `IDEAS.md` claimed Mac/web/iPad users
   have "no way to see" this. Refuted with sources: Word for Mac has Review > All Markup and a
   Reviewing Pane *with counts*, a Preferences setting that **warns before sending** a file
   with tracked changes, and Picture Format > Compress Pictures > "Delete cropped areas of
   pictures"; Word's Crop tool greys out and shows the recoverable region; LibreOffice is free
   on every platform and shows crop values numerically. The shipped copy makes the narrower
   claim that survives measurement: the **one-pass** Document Inspector is Windows-only
   (Microsoft's own wording), it removes without showing, and no free client-side tool audits
   every image in a document at once. The query itself returns zero third-party tools.
2. **A real bug in already-shipped code.** `comments.ts` tested `w15:done` against `'0'` and
   `'false'` only. `ST_OnOff` has three false spellings, so `done="off"` reported a **live**
   comment thread as resolved. Fixed; a regression test fails when reintroduced.
3. **The `mc:AlternateContent` double-count reaches the headline feature.** Word writes a text
   box's content twice. The refuter added the case the report missed: in a real file the two
   branches hold a `w:drawing` and a `w:pict` of the *same picture*, so a naive walker reports
   two cropped photographs where there is one — with two different ratios, because the
   encodings round differently.
4. **`a:srcRect` is usually empty** (9 of 12 in a measured corpus), so a crop is reported only
   on a present non-zero inset.
5. **`w:vanish` toggles off in the wild** — LibreOffice's exporter emits
   `<w:vanish w:val="false"/>`, so presence-testing would report a document full of hidden text
   that has none.
6. **The rsid claim was verified and strengthened.** Microsoft's implementer note says Word
   generates rsids at random; independently, the table was measured *sorted ascending* in 12 of
   12 real files, so the observable order is a sort and not a history. Two independent reasons.
   No chronology, enforced by a structural CI gate.

**Two bugs fixed during browser verification, one of them in production:**

1. The reveal images carried `loading="lazy"`, which saves no network on a `data:` URL and left
   the headline finding rendering as four empty boxes in a background tab (`complete: false`
   indefinitely). Removed.
2. **The feedback link vanished after the first interaction.** Caught on the live site: the
   footer read `… more tools & sites · Feedback` on first paint and `… more tools & sites`
   after loading a document. The hosted widget self-mounts into `.footer-inner` on

## Not verified

- **No real Word-produced file was tested.** Every fixture, including the sample, is
  constructed from hand-written XML parts. The walkers are verified against XML shaped the way
  the ISO/IEC 29500 schemas and Microsoft's documentation specify, and against a 12-document
  public corpus analysed during review — but not against a file that a given version of Word,
  Word for Mac, Word on the web, Google Docs or Pages actually emitted. The highest-value
  follow-up is one real file from each, each containing a tracked change, a threaded comment, a
  resolved comment, a cropped image and hidden text.
- Whether `w:moveFrom` uses `w:delText` or `w:t` is not settled by the schema and the sources
  disagree; docxray reads **both** from every run, which makes the question moot.
- The `w:highlight`-beats-`w:shd` precedence is asserted by documentation, not measured in Word.
