## What shipped, and how it differs from the spec

**The spec's central product decision was inverted.** It said to lead on the always-present metadata.
The incumbent research said the opposite and it was followed:

- The **metadata-viewer shelf is a commodity** — six free, no-signup, explicitly client-side PDF metadata
  viewers. TrustPDF's *Inspect PDF* is free, client-side and **already counts incremental revisions**;
  its bundle was downloaded and grepped (`s=[...t.matchAll(/%%EOF/g)].map(e=>e.index||0)`).
- The **revision-recovery shelf is empty in the browser.** pdfresurrect and peepdf are CLI; qpdf
  explicitly cannot (issue #22); npm has nothing that reads incremental updates; TrustPDF stops at
  counting — no extraction path anywhere in its bundle, and its signature analysis is *hardcoded*
  (`hasByteRange:!0, coversWholeDocument:!0, subFilter:"Unknown"`), so it cannot make a ByteRange claim
  at all. Grep for `xmpMM`/`softwareAgent` across its whole bundle returns zero hits.

So peelback leads on recovery; the producer chain is strong supporting evidence rather than the headline.
The spec's deferred "150 DPI pixel-diff" was **not** deferred — a **side-by-side page reader** shipped
instead, because a difference the reader can *see* beats an inference they must trust.

## The measured base rate, which set the entire tone

Six official IRS/HUD/GPO PDFs were measured: **five carry more than one `%%EOF`, and in each of those
five at least one marker is not an earlier version of the document.** A naive extractor materialises a
~500-byte, zero-page "revision 1" on essentially every linearised file — one that still contains `/Root`
and an in-range `startxref`, so the obvious "does this look like a PDF?" check does not catch it.

Consequences, all shipped:

- **No verdict vocabulary anywhere**, enforced by `tests/language.test.ts` over the interface copy, the
  glossary, the producer table, every finding generated from every sample, and all three exports.
- A **permanent, non-dismissable base-rate panel** above the findings.
- The claim is stated as a **marker** count, never a save count. An earlier draft said "five had been
  saved more than once"; the adversarial pass caught that as the same overcount the tool exists to
  correct, and it was fixed in six places.
- A **one-time interstitial before the first recovery**, because revision recovery is an un-redaction
  engine: a black rectangle drawn over text and saved *is* an incremental update, so the account number
  and the third-party payees underneath it come back with it.
- An **applicant-facing export**, because a landlord inspecting a document handed to them directly is not
  a consumer-reporting agency (15 U.S.C. §1681a(d), (f)) and the subject otherwise gets no notice, no
  named source and no right of reply.
- Every caveat is written **into** `report.html`, uncollapsed, above the findings — the report is the
  thing that gets forwarded stripped of everything the user read on screen.

## Architecture decisions

**The PDF reader is first-party**, which was not a preference:

- pdf.js re-indexes every object when a cross-reference table does not parse, and **there is no option to
  stop it.** `stopAtErrors` sounds like one and is not — it is converted to an `ignoreErrors` flag placed
  only inside the content-stream evaluator's options, and an A/B test on a broken prefix returns
  byte-identical results either way. `XRef.readXRef()` additionally *swallows* per-section failures and
  only throws if it got no trailer at all.
- **"It renders" is not evidence in any engine.** Sweeping 79 truncation prefixes of a two-revision file,
  four structurally invalid ones — cut mid-cross-reference-table — loaded cleanly and returned plausible
  text. Apple CoreGraphics thumbnailed the same bytes.

So the strict first-party parse is the only gate, and pdf.js can add a caveat but never promote a
revision. Modules: `lexer` (strict object reader), `xref` (classic tables, `/Type /XRef` streams,
`/XRefStm` hybrids, `/Prev` walking with a visited set), `predictor` (PNG un-filtering), `doc` (object
streams, page tree, text-string decoding), `revisions` (boundaries + three gates + classification),
`signatures`, `xmp`, `producers`, `dates`.

**Linearisation is detected structurally.** `/Prev`-chain walking alone does *not* defeat it — both
sections are legitimately on the chain. The shipped test needs no `/Linearized` keyword (which can itself
sit inside an attachment): **a section whose `/Prev` points forward is Annex F's first-page table.**

**`fflate.decompressSync`, not `DecompressionStream`.** The latter **throws on trailing bytes** by
specification (whatwg/compression#76; Chrome: "Junk found after end of compressed data"), and a PDF
stream's `/Length` is routinely generous. This has already broken a production PDF parser —
mozilla/pdf.js#18876 is exactly that error. An earlier code comment justified fflate on truncation
tolerance; that was measured false and corrected.

**Offsets are measured from `%PDF-`, not byte 0.** §7.5.2 permits junk before the header, and mail
gateways and scanners leave it there. Handled, warned about, and covered by two tests.

**`exifr` was dropped and embedded-image EXIF cut from v1** — exifr's last publish is 2021-08-05 (~5 years
stale), and only 9.4% of PDFs contain any EXIF-bearing JPEG. A 130 KB library for fewer than one document
in ten.

**pdf.js is split into its own Rollup chunk** so the build gate's third-party exemption is narrow: pdf.js
legitimately carries an XHR transport (never given a URL here; `useWorkerFetch: false`), and bundled
together that dead code would have forced the gate to be loosened over the whole application. First-party
output is 84 kB; the gate now checks 3 first-party scripts in full and asserts the split still exists.

## Privacy model

- **Protected:** the PDF is read in the tab and never uploaded; recovered versions live in memory only;
  nothing is written to disk (no IndexedDB, localStorage, sessionStorage or OPFS); no `console.*` survives
  the build; fully offline after first visit.
- **Not protected:** recovering an earlier version can undo a redaction — stated plainly in the privacy
  modal and gated by an interstitial; downloads are ordinary files; peelback cannot tell whether a
  document is genuine.
- **Trust surface:** GitHub Pages over TLS, the Cloudflare Web Analytics beacon, and
  feedback.benrichardson.dev only on an explicit Send. The gate fails the build if the CSP grants a
  fourth origin.
- The zero-backend rule is documented as a **legal boundary**, not a preference: an upload would put a
  named person's un-redacted bank statement plus a record of the check on a server, and furnishing that
  to third parties engages the consumer-reporting definition at §1681a(f).

## Errors & Resolutions

1. **Build gate failed: `XMLHttpRequest` in the app bundle.** pdf.js's dead network transport had been
   bundled into `index-*.js`. Resolved by splitting pdf.js into its own Rollup chunk so the exemption is
   narrow, plus a gate assertion that fails if that split ever disappears.
2. **pdf.js wedged in the hidden preview tab.** Diagnosed to rAF never firing; fixed with the fallback
   and the 15 s budget described above.
3. **Timeout treated as rejection**, withholding downloads. Fixed — see above. This is the most valuable
   defect the browser pass found.
4. **Overclaimed base rate.** An adversarial refuter caught "five had been saved more than once" as a
   restatement of the very overcount the tool corrects. Rewritten in six places as a marker count, with
   the test updated to assert the corrected wording.
5. **False comment in `inflate.ts`** claiming fflate tolerates truncation. Measured false; rewritten with
   the real reason (trailing-byte tolerance, which `DecompressionStream` lacks by specification).
6. Three test expectations corrected against the implementation (two `%%EOF` counts, one Paeth branch).
