# Fleet SSL sweep — 2026-08-02

First run of the `fleet-ssl-repair` routine, executed manually.

**Checked:** 163 (sites 69 · games 46 · tools 48)
**Healthy at start:** 132 · **Broken:** 31 · **Fixed:** 7 · **Still broken:** 24

## Root causes found

### 1. All three factories polled the wrong field (fixed)

`gh-site-factory`, `gh-game-factory` and `gh-tool-factory` all confirmed TLS issuance by polling
`.https_enforced`. That field is `false` even on perfectly healthy properties, so the poll never
succeeded, each factory timed out and shipped anyway, and the property went live with a stalled
certificate — dead in every browser. All three now poll `.https_certificate.state == "approved"`.

### 2. Let's Encrypt rate limit — the binding constraint (NOT fixed; structural)

Let's Encrypt issues **50 certificates per registered domain per 7 days**. Every property is a
subdomain of the same registered domain, `benrichardson.dev`, so all 163 share one budget.

Steady-state burn:

| Source | Certs/week |
|---|---|
| 3 factories × 1 new property/day | 21 |
| Renewals of 163 properties (90-day certs) | ~13 |
| **Total before any repair** | **~34 / 50** |

This is why cycling 20 stalled domains recovered exactly **5** and left 15 frozen with zero state
movement across 5 minutes of polling — the token bucket had ~5 tokens left.

**Projected hard failure:** solving `50 = 21 + N × 0.078` gives **N ≈ 373 properties**. Past that,
renewals plus new builds permanently exceed the limit and nothing can obtain a certificate. At
3/day from 163, that is roughly **mid-October 2026**. Certificate cycling cannot fix this.

Options (architectural — for the user to decide):
- spread properties across multiple registered domains (`ben.gy` has its own 50/week budget)
- serve properties as paths under one host (`lab.benrichardson.dev/{slug}`) — one certificate
- move hosting to Cloudflare (Universal SSL covers `*.benrichardson.dev` with one certificate)
- slow the factories

## HTTPS enforcement

Enabled on **66** properties whose certificate was `approved` but had `https_enforced: false`
(GitHub Pages leaves this off by default, so plain `http://` was served without redirecting).
Note the API field is typed: `-F https_enforced=true`, not `-f` (which 422s).

## CNAME-file audit — no action needed

An initial audit flagged 7 properties as missing `public/CNAME`. **All 7 were false positives.**
`artemis-tracker`, `benrichardson.dev`, `leader-skills`, `pipboy`, `pullshark-board`,
`voynich-investigation` and `worldcupinvitations` are root-served sites (`build_type: legacy`,
no `public/` directory) with a correct root `CNAME` — the right location for that layout.
The routine's Class E check now branches on build type. Treat these 7 as a known-good control set.

The 47 Vite-based tools all have correct `public/CNAME`, and it is confirmed to survive into the
deployed artifact (`/CNAME` is served on live properties).
