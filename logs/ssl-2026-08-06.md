## SECURITY — `metascrub-app.benrichardson.dev` has been taken over

**A stranger is serving Indonesian gambling spam from a `benrichardson.dev` subdomain, and
the tool registry was linking to it.**

`metascrub` was registered at `metascrub-app.benrichardson.dev`, but the repo's Pages
`cname` and its `public/CNAME` both say `metascrub.benrichardson.dev`. When the property
moved, the DNS record for the old hostname was left pointing at `ben-gy.github.io` with
nothing of ours claiming it — a dangling CNAME. Someone else claimed that hostname on their
own GitHub Pages repo and has been serving it since:

```
$ curl -s https://metascrub-app.benrichardson.dev/ | grep -o '<title>.*</title>'
<title>Tombolwd # Toto Slot 10K Pilihan Simpel Buat Cari Cuan Maksimal</title>

$ curl -sI https://metascrub-app.benrichardson.dev/
server: GitHub.com
last-modified: Mon, 27 Jul 2026 11:40:54 GMT

$ openssl s_client -connect metascrub-app.benrichardson.dev:443 …
subject= /CN=metascrub-app.benrichardson.dev
issuer=  /C=US/O=Let's Encrypt/CN=YR2
notBefore=Jul 15 14:12:37 2026 GMT
```

The certificate was issued **2026-07-15**, so the hostname has been in someone else's hands
for three weeks. Note that their certificate — and every renewal of it — is issued against
`benrichardson.dev` and therefore **spends from the fleet's own 50/week Let's Encrypt
bucket**.

**Not remediated by this run.** Removing the DNS record is the fix, but the standing
guardrail is to delete a record only when GitHub reports the hostname *unclaimed*, and this
one is claimed — by them. Deliberately deleting a record someone else is actively serving is
a decision for the operator, not for an unattended sweep. It is reversible and it is one
call:

```bash
CF=$(cat ~/.claude/secrets/cf-benrichardson-token); ZID=bf71cf2904d22db3443bb471e5dbdde2
ID=$(curl -s -H "Authorization: Bearer $CF" \
  "https://api.cloudflare.com/client/v4/zones/$ZID/dns_records?name=metascrub-app.benrichardson.dev" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["result"][0]["id"])')
curl -s -X DELETE -H "Authorization: Bearer $CF" \
  "https://api.cloudflare.com/client/v4/zones/$ZID/dns_records/$ID"
```

What *was* done: the registry URL was corrected to `https://metascrub.benrichardson.dev`, so
the tool index no longer links to the spam. That reclassifies `metascrub` as broken — its
real hostname is sitting at `authorization_created` like the rest of the backlog.

### The script cannot currently see this class of failure

`--fix-registry` corrects a registry URL when the probe *fails*. A hijacked hostname returns
`200` over valid TLS, so the property scores as healthy and the mismatch is never examined.
The check that catches it is structural, not behavioural: **registry host ≠ the repo's Pages
`cname`**. Sweeping that comparison across all 173 properties found exactly one mismatch —
this one — so the fleet is otherwise clean.

The zone was also swept for the underlying condition. Twelve records `CNAME` to
`ben-gy.github.io` without a matching Pages `cname` in any registry:

| Hostname | Serves | Verdict |
|---|---|---|
| `brood`, `charsight`, `conflictmap`, `pagewell` | our content | hand-built sites, kept out of the registries on 08-02 — fine |
| `lab`, `www` | our content | fine |
| `au-approvals`, `au-baby-names`, `au-inflation`, `au-ndis-watch`, `vic-rents` | GitHub 404 "Site not found" | **superseded hostnames, unclaimed — safe to prune, 5 records** |
| `metascrub-app` | someone else's spam | **taken over, see above** |

The five unclaimed records are the same shape as the takeover that already happened, and
they free 5 of the zone's 5 remaining slots. They were not deleted here because the 08-04
session explicitly logged the superseded records as an operator decision; that decision is
now also a security one.

The 08-04 amendment's test — "if the bucket were exhausted, new properties would stall too"
— now has a direct measurement behind it rather than an inference. Deriving issuance dates

**Thirteen tokens of headroom**, and one of them was spent this morning on `au-advisers`,
which went from shipped to `approved` + enforced + 200 in minutes. Meanwhile all six backlog
properties held an undisturbed authorization for a full 24h and not one state advanced.

That combination rules out the budget. It also rules out configuration: DNS for the five
fresh hostnames is byte-identical to the healthy controls (`CNAME` → `ben-gy.github.io` plus
the four A records, unproxied), all six serve `200` over plain HTTP so the HTTP-01 path is
reachable, and Pages reports `build_type: workflow`, `source main:/`, correct `cname`.

**What is left is that these six hostnames specifically will not complete validation.** Five
of them are *fresh* hostnames minted on 08-04, which is what makes this awkward: the 08-04
hypothesis was that the block is hostname-scoped and a fresh hostname clears it, and on that
evening eight fresh hostnames did issue within a minute. These five were minted the same way
in the same session and have not. The distinguishing fact is that these five are exactly the
ones the 08-05 08:12 run stomped — their first authorization was abandoned at ~9h old. So
the open question is whether abandoning an authorization taints the hostname it was opened
against.

If it does, the sequence is self-perpetuating: cycle → abandon → taint → cycle again, which
is the loop this routine has been running. **Cycling these five again is the one action most
likely to be harmful, and tomorrow's run will do exactly that** — they cleared the 24h
cooldown mid-morning today. Recommend `--no-cycle`-ing them, or better, leaving all six
strictly untouched for a week and re-probing, which is a test that costs nothing and
distinguishes "tainted, ages out" from "permanently dead".

`noisewell` is the control: it is the one property never moved to a fresh hostname (the zone
was at 200/200 on 08-04), so it has been sitting on its original blocked hostname the whole
time. It behaves identically to the five fresh ones.
