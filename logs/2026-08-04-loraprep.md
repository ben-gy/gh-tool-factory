## Tool Details

- **Name:** Loraprep
- **Repo:** ben-gy/loraprep
- **Category:** images
- **Audience:** People training LoRAs on photographs they cannot upload — faces, client
  photography, unreleased product shots. The alternative on offer is renting a cloud GPU to run a
  Python script they did not write.
- **Stack:** Vite 7 + vanilla TypeScript + Vitest, 171 unit tests
- **Browser APIs:** module Web Workers (decode pool + separate inference worker), WebGPU/WASM via
  onnxruntime-web, createImageBitmap + OffscreenCanvas, transferable ArrayBuffers, File System
  Access, `DataTransferItem.webkitGetAsEntry`, Cache API, Web Share, Service Worker
- **Worker strategy:** a bounded decode pool feeding ONE inference worker, main thread as the pipe
  (and therefore the backpressure). The separation is not stylistic — see below.

## Privacy Model

- **Protected:** every image is decoded, measured, embedded and packaged in the tab. The model runs
  on the user's machine. No cookies, no fingerprinting, one localStorage key (`loraprep.theme`).
- **Not protected:** the model is fetched once from Hugging Face (3 files, 22,877,205 B, pinned
  revision SHA); the exported ZIP carries the original image bytes **including EXIF**; the report
  and `metadata.jsonl` carry original file paths.
- **Trust surface:** the static bundle + TLS; the pinned model, checked at boot against a reference
  vector committed to the repo; ONNX Runtime WASM binaries served **from our own origin** rather
  than jsDelivr.

Verified cold in-browser: after clearing all caches and running the full pipeline, the
`transformers-cache` contained exactly the three pinned `huggingface.co` URLs plus two same-origin
`/ort/` files. No text tower, no tokenizer, no CDN.

## Architecture Decisions

Nine agents ran in a Workflow (5 research lanes, 3 adversarial refuters, 1 synthesis), all pinned to
Opus 5. **All three refuters returned `refuted: true`**, and each one changed the build.

### 1. The vision model is not allowed to set anything aside

The idea file specified union-find over CLIP cosine as a deletion rule. Measured against
`google/dreambooth` (158 hand-curated photographs, zero duplicates by construction):

| | cosine |
|---|---|
| Different photos of the same subject (must keep) | median 0.804, p95 0.934, p99 0.972, **max 0.9916** |
| Different subjects | median 0.243, max 0.919 |
| True duplicate, 2× upscale / re-encode q40 | 0.981 / 0.956 |
| True duplicate, **mirror flip** / rot 5° / greyscale | 0.878 / 0.860 / 0.855 |
| True duplicate, watermark | 0.726 |

The distributions overlap in the wrong direction. At 0.90: misses flips, rotations, greyscale, crops
and watermarks, *and* falsely condemns 49 of 342 same-subject pairs. At 0.98: catches 1 of 13
duplicate families — the one dHash finds at 1 bit. Net safe recall added by the 22.9 MB model as a
*deletion* signal: **zero**.

Union-find over those edges was worse: at 0.90 it collapsed six visually distinct photographs of one
bowl into a single survivor, through a chain containing a pair at 0.809 — nine hundredths below the
threshold that formed the cluster — removing 35 of 158 hand-curated images.

**Shipped instead:** dHash-64 union-find (zero false matches across all 12,403 pairs at Hamming ≤ 5)
does the automatic part; the model produces ranked *pairs* for review with nothing pre-selected, in
its own section, with the numbers above stated in the UI.

### 2. Sharpness alone picks the worst file

Caught by my own browser dry-run before the refuters reported. Variance of the Laplacian rises as
JPEG quality falls, because blocking artefacts are high-frequency energy: the same photograph at
q92/82/76 scores 40/53/73, so the keeper was the most damaged copy in **every one of the eight**
sample groups. A 3×3 pre-filter was tried and measured — it does not fix it (3.44/5.94/7.24), since
blocking is structural rather than noise.

**Shipped:** sharpness decides only what is *in focus* (blurred and downscaled frames score 6–17% of
their group's best — a wide empty gap, so the 0.35 cut is a measurement not a tuned constant), then
the most bytes per pixel wins, bucketed by powers of two so a real burst still decides on sharpness.
After the fix, all eight groups keep the high-quality original.

### 3. Decode and inference must not share a thread

Alternating `createImageBitmap` with `session.run` degrades ORT inference from 138 ms to ~1,050 ms —
7.6×, reproduced in Chrome 148 and 150, with images as small as 2.8 MP. Chunking 8-and-8 does not
help (1,037 ms); only full phase separation restores 141 ms.

**Shipped:** a decode-worker pool feeding one inference worker that never touches an image decoder,
plus a watchdog that rebuilds the session (791 ms) if it degrades past 2.5× baseline. Measured on
the sample: **10.6 s → 5.0 s**.

Also from that lane: `resizeWidth`/`resizeHeight` on `createImageBitmap` is a **no-op or slower** in
Chromium (338 ms vs 285 ms full decode). Kept for correctness on engines that honour it, never
quoted as a saving.

### 4. The model file the idea specified is broken

`vision_model_quantized.onnx` (11,846,843 B, int8) — the file the idea file named as its headline
choice — has cosine **0.093** against its own fp32 output, and gives four unrelated photographs
pairwise cosines of 0.73–0.88 where fp32 gives 0.08–0.17. Every image looks like every other one.
The repo's own `config.json` quietly steers around it
(`transformers.js_config.dtype.vision_model = "fp32"`). Both proposed q4f16 alternatives **fail to
load at all** under ORT-web's WASM graph optimiser (`SimplifiedLayerNormFusion` crash).

**Shipped:** fp16 (22,876,479 B, cosine 0.99999 to fp32, and on the single-threaded WASM tier
quantisation buys no speed at all — fp32 137 ms, fp16 144 ms, q4 145 ms, q8 171 ms). And the tool
does not take its own word for it: a boot self-check embeds a code-generated probe and compares
against a reference vector committed to the repo, rejecting any backend below 0.985. Verified
locally in Node — fp16 0.99999, q4 0.98749, **q8 0.48020** — and live in-browser at 0.99972 on
WebGPU. That check is what makes trying WebGPU first defensible.

### Other decisions

- **Self-hosted ORT binaries.** transformers.js silently sets `wasmPaths` to `cdn.jsdelivr.net` on
  import. Overridden to `/ort/` (copied from node_modules at build time, gitignored), which is why
  the CSP names no CDN and why the offline claim is true. The ORT base URL is resolved on the **main
  thread** from `document.baseURI` — inside a worker `import.meta.env.BASE_URL` resolves against the
  worker's own `/assets/` path and ORT fails with "no available backend found".
- **A Vite plugin drops the dead 23.5 MB WASM asset** Vite emits from ORT's
  `new URL(..., import.meta.url)`, which is never fetched.
- **First-party header parser** for true pixel dimensions, so the pipeline never needs a second
  full-resolution decode just to read two numbers.
- **kohya conventions read from sd-scripts' own source**, not from blog posts: the folder name is
  parsed by `split('_')`, a top-level wrapper folder is required, `glob_images` is non-recursive,
  captions are `lines[0].strip()` so they must be one line, and **UTF-8 without BOM** because
  Python's `utf-8` codec leaves U+FEFF glued to the trigger word. `metadata.jsonl` carries the
  caption under **both** `text` and `prompt` because diffusers has no single convention.
- **The ZIP refuses rather than corrupts.** fflate writes no ZIP64 and silently wraps the
  central-directory offset mod 2³² above 4 GiB; the writer checks first and explains.

## Test Results

- Tests written: **171** across 8 files
- Tests passed: **171**
- Tests failed: 0

Four real bugs were caught by tests or the dry-run rather than by review:

1. `conceptDirName('')` produced `5_image` — `safeSegment`'s own "never empty" fallback leaked into
   the class token, which would have trained the concept on the wrong word.
2. `assignExportNames` lowercased the extension on a collision (`IMG_0001_2.jpg` from
   `IMG_0001.JPG`).
3. `safeSegment('../../etc/passwd')` left an interior `..`. Harmless in a single segment, but the
   property "the output contains no `..` at all" is checkable at a glance, so dot-runs now collapse.
4. **Set-aside could not be undone.** Every rebuild chained off the *previous* rebuild, so an image
   already marked `excluded` no longer matched the `verdict === 'kept'` branch and could never come
   back. Rebuilds now always start from the pristine grouping output.

Two test-environment traps were fixed honestly rather than papered over: jsdom's `Blob` has no
`arrayBuffer()`, so the ZIP tests run under `@vitest-environment node` rather than having a fallback
added to ship code; and the first blur fixture left an unwritten border of zeros, which put a
255-step edge round the frame and made the "blurred" image score *higher*.

## Errors & Resolutions

| Error | Resolution |
|---|---|
| Idea file's headline model file is numerically broken (cos 0.093) | Switched to fp16; added a committed reference vector + boot self-check that rejects any backend below 0.985 |
| Idea file's quality-tier files (q4f16) fail to load under ORT-web WASM | Not shipped; MobileCLIP-S0 fp16 is smaller AND faster AND more accurate than both alternatives |
| Idea file's CLIP-cosine union-find would delete genuinely distinct photos | Restructured: hash-only auto-grouping, model output demoted to review-only ranked pairs |
| Idea file's "20–50 ms per decode" is 4–10× optimistic (measured 180–210 ms on a 12 MP photo) | Pre-run estimate now scales on average file size and is a wide range, replaced by the live measured rate; the log and PR say the throughput figures come from a 512 px synthetic sample |
| Sharpest-wins keeper picked the most JPEG-damaged copy in 8/8 groups | Two-signal keeper rule (in-focus gate, then bytes per pixel bucket) |
| Interleaved decode + inference degraded ORT 7.6× | Split into a decode pool + a dedicated inference worker; 10.6 s → 5.0 s on the sample |
| transformers.js defaults `wasmPaths` to a third-party CDN | Self-hosted `/ort/` binaries + explicit override; verified no jsDelivr request |
| Vite emitted a dead 23.5 MB WASM asset into every deploy | A `generateBundle` plugin drops it |
| Set-aside could not be undone | Rebuilds now start from the pristine grouping, not from the previous rebuild |
| Stale service worker from a previous tool served another app's shell on the preview port | Unregistered + caches cleared (the recurring preview trap) |
| Browser-pane screenshots return a black frame once scrolled past the first viewport | Not a page bug — verified by DOM inspection and by hiding the hero to bring the grid into the first viewport |

## Honest gaps

- **No run on a large real-world photo library was possible in this pipeline.** All throughput
  figures for real photographs come from the adversarial agent's first-party browser measurements on
  40 distinct 12 MP JPEGs, not from a Loraprep run; Loraprep's own measured run is 36 synthetic
  512×512 images.
- **The WASM fallback path was not separately exercised in a browser here** — this machine has
  WebGPU and it passed the self-check, so that is the path that ran. The WASM tier is what the model
  benchmarks were measured on, in Node.
- The sample dataset is procedurally generated, not photographic, and the UI says so.
