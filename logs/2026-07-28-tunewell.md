## Idea Source
Researched. IDEAS.md was empty. Reviewed the registry and found a heavy file→file
bias (images, PDF, media) with only a handful of live-sensor tools; the last three
runs (wavewell, ditherwell, vectorwell — with noisewell the sensor tool before them)
were all file-in/file-out. Applying principle #6's "what if the input were not a
file?" test, the single highest-demand microphone tool the fleet had never built was
an **instrument tuner** ("guitar tuner online" is one of the highest-volume searches
in this whole category). It's a true mic-sensor tool, the DSP (MPM pitch detection)
is non-trivial and pure-function testable, and it clears the artefact bar two ways:
the live cents/note reading you act on, plus a downloadable reference-tone pitch-pipe
WAV (mirroring voxwell's export-a-.wav pattern).

## Tool Details
- **Name:** Tunewell
- **Repo:** ben-gy/tunewell
- **Category:** sensor-tools (media/music)
- **Audience:** Hobbyist musicians who want a fast, ad-free, private tuner that never streams their mic.
- **Stack:** Vanilla TypeScript + Vite + Vitest. Zero runtime dependencies.
- **Browser APIs:** getUserMedia, Web Audio (AnalyserNode, OscillatorNode, OfflineAudioContext), Web Workers, Canvas 2D, File System Access, Web Share, Clipboard, Service Worker (PWA).
- **Worker strategy:** live tuning on the main thread via a 20 Hz setInterval loop (rAF stalls in a hidden tab); whole-recording pitch trace in a dedicated Web Worker.

## Privacy Model
- **Protected:** Microphone audio is turned into a single frequency number per slice, in memory, and discarded — never recorded, saved, or uploaded. Uploaded recordings decoded locally. Reference tones synthesised on-device.
- **Not protected:** Absolute concert-pitch accuracy depends on the microphone and room (the reference-A control + downloadable pipe address this); the initial page load is served by GitHub Pages, whose CDN sees the visitor's IP.
- **Trust surface:** static bundle + TLS; cookieless Cloudflare Web Analytics beacon (audio never sent to it); feedback only when the user presses Send.

## Architecture Decisions
- **Pitch detection is first-party (no library).** Implemented McLeod's Pitch Method
  (NSDF) with the autocorrelation term computed via a hand-written radix-2 FFT
  (O(N log N), cheap enough for ~20 Hz on a phone) and the normalisation term via a
  running sum-of-squares. Key-maxima picking with a 0.9 threshold avoids the octave
  errors naive autocorrelation makes; parabolic interpolation gives sub-cent accuracy.
  Keeping it a pure function (`Float32Array → {frequency, clarity}`) is what makes the
  sensor logic exhaustively unit-testable without a real microphone.
- **Two artefacts, both real files.** The pitch-pipe WAV (rendered via a first-party
  16-bit PCM encoder + harmonic tone synth) is the primary artefact; an uploaded
  recording additionally produces a pitch-over-time PNG + CSV report.
- **The file/tune-by-ear paths are first-class**, not consolation — a denied mic still
  reaches the full pitch pipe (play + download) and the recording analyser.
- **iPhone earpiece note** shown (not a speaker toggle, which cannot work): while a mic
  stream is live iOS routes AudioContext output to the earpiece and no web API can move it.
- Vanilla TS over React — no multi-pane state; a 4-state machine (start/live/analyzing/report) is plenty.
