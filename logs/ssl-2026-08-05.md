## Incident — the 08:12 run stomped five in-flight authorizations

The table above is from the **second** pass of the day, after a fix. The scheduled 08:12 run
did damage, and the mechanism is worth recording.

The 08-04 evening session moved 14 stuck properties to fresh hostnames **by hand**. That work
never touched `state.json`, so the cooldown ledger still held the timestamps of the *previous*
hostnames — 2026-08-02 14:16, i.e. 66h old. The 08:12 run read those, judged six properties
long out of cooldown, and cycled them. Five were fresh hostnames whose authorizations had been
open for about **nine hours**:

| Property | Hostname cycled at 08:12 | Age of the authorization it abandoned |
|---|---|---|
| au-inflation | au-cpi-explorer | ~9h |
| au-approvals | au-build-approvals | ~9h |
| au-insolvency | au-insolvency-tracker | ~9h |
| facet | facet-dice | ~9h |
| au-baby-names | au-name-trends | ~9h |

This is exactly the harm the cooldown exists to prevent — abandoning a live ACME request and
spending another token from the scarce budget. `au-baby-names` issued anyway and is now
`approved`, enforced and serving 200. The other four restarted from zero.

The run then compounded it by reporting `NOT ISSUING — … 66h` against those same properties.
That verdict is what the analysis doc tells the next operator to act on, and the recommended
action for a hostname that will not issue is to **move it to another fresh hostname**. Acting
on it would have burned four more DNS records out of a zone that is already at its 200/200 cap
— on hostnames that had never actually had an undisturbed 24h to begin with.

**Fixed in `lab@scripts/ssl/fleet-ssl.mjs`.** The cooldown ledger is now keyed on
`{ts, host}` rather than a bare timestamp:

- A hostname the script did not cycle itself is **adopted, not cycled**. If a cert flow is
  already open on it, its start time is unknowable, so the script stamps first-observation and
  lets it serve a full untouched cooldown. Only a host with no flow at all (`certState` null)
  is cycled on sight — that is the documented case where cycling is the necessary trigger.
- `NOT ISSUING` is only reported when the recorded hostname is still the one in play, so an
  elapsed time is never attributed to a hostname that has since been replaced.
- Legacy bare-timestamp entries are treated as host-unknown, so they adopt rather than act on
  a timestamp that cannot be attributed.
- State is persisted even when nothing is cycled, since an adoption is the record that starts
  a hostname's cooldown.

The re-run cycled only `toolwright`, which genuinely had no `https_certificate` object at all,
and held the other six in cooldown.
