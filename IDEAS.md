# Tool Ideas

Add client-side browser tool ideas here. The scheduled task will pick the first idea from this list, build it, and remove it. One idea per line — be as brief or detailed as you like, the task will flesh it out.

**The bar every idea must clear:**

- **Zero runtime backend.** GitHub Pages only. GitHub Actions at build time is fine — nothing at runtime.
- **Pushes a browser API to do something genuinely useful.** Web Crypto, WebCodecs, WebRTC/DataChannel, WebTorrent, File System Access, Origin Private File System, WASM (ffmpeg.wasm, pdf-lib, jsquash, onnxruntime-web, transformers.js), Web Audio, Web Speech, Web Share, WebUSB, WebBluetooth, WebSerial, WebHID, WebGPU, OffscreenCanvas, Streams, Compression Streams. The more ambitious the capability, the better.
- **Privacy-first.** Data never leaves the device. The UI must say so explicitly and the "How it works" / "Threat model" modals must back it up.
- **Solves a real problem someone would Google for.** Not a novelty demo. Someone is stuck, they type a query, this tool is the best answer. **This tests demand, not seriousness** — "voice changer online" and "spirit level app" are real, high-volume searches. Playful is fine; unwanted is not.
- **The user leaves with an artefact.** A file, an image, a number they can act on, a link they can send. This is the line between a playful *tool* and a toy.
- **Not CSS-only.** Must have real logic — compression, encryption, codec work, P2P transfer, ML inference, signal processing. No pure-CSS utilities.

**The input does not have to be a file.** The microphone, camera, gyroscope and accelerometer are all
local, zero-backend and a perfect fit for the privacy promise — a live-sensor tool is the most honest
version of "your data never leaves the device". Ideas in that register are very welcome.

The north-star is **[Dropwell](examples/dropwell/)** — end-to-end encrypted peer-to-peer file transfer with no server, using WebTorrent + Web Crypto. That level of ambition is the baseline, not the ceiling.

## Standing note for any P2P idea

Any P2P idea in this file follows the Dropwell pattern so "zero runtime backend" holds honestly: **peer discovery/signalling rides public infrastructure** (WebTorrent trackers or nostr relays via a trystero-style layer) — no dedicated server, nothing we host at runtime. WebRTC gives DTLS on the wire, but the **hard privacy win is an application-layer E2E layer on top**: derive a key with Web Crypto (PBKDF2/HKDF) from a room passphrase that is **never sent to any relay**, encrypt media frames with **Insertable Streams / SFrame** (WebCodecs) and data with AES-GCM, and show a **Short Authentication String** (a few words both sides read aloud) so a malicious relay cannot MITM the handshake. Be honest in the Threat Model modal about the **one real limitation**: NAT traversal uses public STUN, and a symmetric-NAT pair with no TURN relay may fail to connect — we will not add a TURN relay because that would be a backend and would see the (encrypted) traffic. Every P2P idea must still leave an **artefact** (a shareable room link, a local-only recording, a saved file, a delivered payload) — a call with no takeaway is a toy. **Note: the catalogue already has eight P2P tools (dropwell, beamwell, syncwell, castwell, talkwell, meetwell, chatwell, sketchwell). A ninth needs a genuinely different job, not a different noun.**

## Standing note for the AI-builder batch below (added 2026-08-02)

The twelve ideas below were researched and adversarially vetted as a batch (30 candidates, three
independent judge lenses: browser feasibility, catalogue duplication, demand + artefact). Two findings
from that review bind every one of them:

1. **They are ordered deliberately — build them top-down.** The order is high-confidence-and-broad-appeal
   first, riskiest last. Do not reorder to pick a favourite.
2. **Several share an engine, and shipping them back-to-back would make them look like reskins.**
   The embed → one `Float32Array` → brute-force cosine in a Worker pipeline underlies searchpack,
   chunkforge, leakspot and topicgap; the `@huggingface/jinja` + `@huggingface/tokenizers` +
   ungated-mirror-registry renderer underlies chatprint, runledger and epochcost. **Never ship two
   tools from the same group in the same week**, and where an engine already exists in a shipped
   sibling, say so in the plan rather than pretending it is new work. This is the collate/pagesmith
   failure mode already recorded in EXPANSION_IDEAS.md.
3. **Two hard technical facts the reviews established, which apply across the batch.** GitHub Pages
   cannot set COOP/COEP, so there is no `SharedArrayBuffer` and **onnxruntime-web silently drops to
   single-threaded WASM** — real transformer embedders manage 20–60 sentences/sec there, not the
   hundreds quoted on model cards. **WebGPU is unaffected** (it does not require cross-origin
   isolation), so the honest pattern is a WebGPU fast path with a static-embedding fallback
   (`static-retrieval-mrl-en-v1` / `potion-base-8M`, ~30 MB int8, EmbeddingBag lookups with no matmul,
   genuinely fast single-threaded). Assume the WASM tier when quoting a throughput number to the user.

## Deferred features — NOT tools, do not build these standalone (added 2026-08-02)

Eighteen further AI-builder candidates were generated alongside the twelve and did not survive.
Ten of them were re-adjudicated individually against the queued twelve and every one was excluded —
mostly for being the same engine pointed at a different file. But several contained one genuinely
good idea each, and that idea belongs to a tool in the queue. **When you build the parent tool,
read this list and fold in its item. Never build one of these as a product of its own.** They are
written without a leading dash precisely so the queue parser cannot mistake them for ideas.

› **chatprint** ← from *lossmask*: a second colour legend over the already-rendered template showing
  which tokens the trainer computes loss on (grey = masked/-100, green = trained), plus an anomaly
  panel for rows where the assistant turn is empty or the template dropped a system message. The
  render is already built; this is a legend and a checker on top of it.

› **chatprint** ← from *cachehound*: a cache-boundary view — longest-common-prefix over the token-id
  arrays of two pasted requests, marking the first divergent token and naming which of the four
  documented cache-breakers caused it (a timestamp in the system prompt, `cache_control` on the
  message instead of the content block, a sub-1024-token prefix, the 5-minute TTL). NOTE the hard
  limit found in review: there is no public local Anthropic tokenizer after Claude 3, so an
  Anthropic-labelled count here must be shown as an ESTIMATE, never as exact.

› **chunkforge** ← from *embedbench*: export `embeddings.f32` + `ids.json` alongside `chunks.jsonl`, so
  the user can load the vectors straight into pgvector without paying to re-embed the corpus
  ($166–$1,079 on a real corpus); plus a second-model column in the hit-rate table, which is cheap
  because chunkforge already loads a second embedder for its quality re-score.

› **scrubjay** ← from *winnow*: a second rule pack for the same streaming engine — the published
  Gopher, C4 and FineWeb quality filters (symbol-to-word ratio, bullet/ellipsis line fractions, mean
  word length, stop-word presence, duplicate-line fraction) with `franc-min` 6.2.0 (~40 kB, no model
  download) for language ID. Same `File.stream()` → `DecompressionStream` → NDJSON → Worker pool,
  same per-rule kill counts and same one-keystroke rule-class triage; only the rule list differs.

› **toolwright** ← from *recast*: point the dialect transpiler at a training file as well as a tool
  belt — ShareGPT / Alpaca / OpenAI / Anthropic / Gemini / DPO conversion reusing the same
  OpenAI `tool_calls` ↔ Anthropic `tool_use`/`tool_result` ↔ Gemini `functionCall` reconciler and the
  same call-id linkage, with the lossiness report saying exactly what each conversion destroys.

› **runledger** ← from *deltaknit*: accept a `.har` or a captured SSE dump as a second ingest dialect,
  reassembling fragmented `tool_calls` argument deltas into valid JSON — and, more valuable than the
  parsing, redact `Authorization` / `x-api-key` / `cookie` headers inside the Worker BEFORE a byte is
  rendered, so a HAR full of live credentials is safe to open.

## Ideas

**The queue is everything below this line, and only that.** Each entry is one line beginning
`- **name** — `. Take the FIRST such entry, delete that line, and build it. The bulleted criteria
higher up this file are the bar, not the queue — never treat one of them as an idea.


- **chatprint** — See the literal string your model actually receives: any model's real chat template rendered and tokenized in the browser, with the context split by system prompt vs tool definitions vs retrieved docs vs history, and a packer that trims it to fit. The situation: your agent just 400ed with "maximum context length is 128000 tokens" and you cannot tell whether the tool definitions, the retrieved chunks or the history ate the window; the query is "how many tokens is my prompt with tools llama 3.1 chat template". Tech: `@huggingface/jinja` 0.5.9 (355 KB) renders the `chat_template` string straight out of any repo's `tokenizer_config.json`; `@huggingface/tokenizers` 0.1.3 (~8.3 kB gzipped, pure JS/TS, zero production dependencies — no WASM, no napi) initialised from `tokenizer.json` fetched anonymously from `huggingface.co/{repo}/resolve/main/` (CORS verified: `access-control-allow-origin` echoes the request Origin; the files are 0.7–2.2 MB, not weights, so first run is fast and mobile is unaffected), with a hand-curated ungated-mirror registry shipped on day one because `meta-llama/*` and `google/gemma-*` genuinely 401 to anonymous fetches while `unsloth/Meta-Llama-3.1-8B-Instruct` and `unsloth/gemma-3-4b-it` serve byte-identical tokenizers; `gpt-tokenizer` 3.4.0 per-encoding standalone builds (o200k_base, o200k_harmony, cl100k_base — 2.05 MB each, lazy-loaded one at a time) for exact GPT-family counts, with Claude labelled ESTIMATE in the UI and the reason printed; `diff` 9.0.0 `diffArrays` over token-id arrays for the model-vs-model view; `config.json` `max_position_embeddings` for the fit check; Cache API so a tokenizer downloads once and the tool then works offline; a Worker pool plus `File.stream()` NDJSON framer for optional bulk mode over a JSONL. Workflow: paste or drop a `messages` array (plus `tools`), pick one or more models, see the byte-exact rendered prompt with every segment colour-coded and counted, then set a budget and watch which segments the packer drops. Artefact: rendered-prompt.txt (byte-exact, what the model sees), token-budget.csv (segment → tokens → % of window, one column per model compared), and messages.trimmed.json — the same conversation packed to fit and ready to send. Privacy: your prompts, tool schemas and retrieved documents never leave the tab; the only network request is an anonymous GET of a public tokenizer file. Displaces PromptLayer Pro at $49/mo (free tier caps datasets at 10 MB) and Agenta Pro at $29/mo; the free substitutes (tiktokenizer, OpenAI's tokenizer page) are OpenAI-only, render no chat template, know nothing about tool blocks and offer no packing. Ship `public/samples/agent-conversation.messages.json` (system prompt + 6 tool definitions + 12 turns + two retrieved docs, ~14k tokens). Hard part: Jinja templates that call `strftime_now`, `raise_exception` or model-specific globals — contain it per model rather than globally, showing the template source and the exact failure instead of a silently wrong count, and keep a visible list of verified-working repos.

- **runledger** — Open an agent run like a file and see where the tokens actually went: per-turn context reconstruction, duplicate tool results caught by MinHash, thrash loops flagged, and a priced ledger of exactly which repeated content you paid for twice. The situation: you spent $47 on Claude Code yesterday and want to know which MCP server's schema block or which CLAUDE.md section was re-sent fourteen times; the query is "why is claude code using so many tokens". Tech: DRAG-AND-DROP OF SESSION .jsonl FILES IS THE PRIMARY PATH per the feasibility review — `showDirectoryPicker` is Chromium-desktop-only, Chrome blocks picking sensitive locations including the home directory, and `~/.claude` is not even visible in the macOS picker without Cmd+Shift+period, so offer the directory picker only as a labelled desktop convenience with that note inline; `File.stream()` piped into a Worker-side NDJSON framer so a 500 MB session is never held whole; V1 INGESTS CLAUDE CODE SESSION JSONL ONLY (it alone supports every feature described — add OTLP/OpenInference/Langfuse dialects later, never on day one); `gpt-tokenizer` 3.4.0 (o200k_base standalone, 2.05 MB, lazy) and `@huggingface/tokenizers` 0.1.3 for per-turn token reconstruction; a first-party 64-bit MinHash over 5-gram shingles for near-duplicate tool results (hundreds of results, not 100k documents, so it costs nothing and runs at millions of shingles/sec in a Worker) plus Web Crypto SHA-256 for exact duplicates; OPFS stores each session as ONE blob, never per-row records, which is the difference between a usable and an unusable browser trace store; Compression Streams for export; a visibly dated, user-editable price table. Workflow: drop one or more session files → reconstruct what was in the context window at each turn from the log of appends and compaction events → hash and cluster repeated content → price it. Artefact: waste-ledger.csv (content hash, occurrences, tokens each, total tokens wasted, dollars), run-report.html (single self-contained file to attach to a ticket), and conversation.pruned.json with duplicate tool results collapsed to references so you can replay and prove the saving. Privacy is load-bearing and absolute: a session log contains every file the agent read — i.e. your entire codebase — which is why people install a Node CLI rather than upload these logs; a browser tab is strictly less friction with the same guarantee. Displaces Langfuse Core $29/mo (Pro $199/mo, 30-day retention cliff on free) and LangSmith Plus $39/seat/month with 10k base traces then $2.50–5.00 per 1k; `ccusage` is free but is a terminal tool that only aggregates cost with no context reconstruction and no duplicate detection. Ship `public/samples/claude-code-session.jsonl` (a real 40-turn session, paths and file contents scrubbed, containing one MCP schema block repeated eleven times). Hard part: reconstructing the turn-N context window from an append-and-compact log — mitigate by validating each reconstruction against the run's own reported `usage` numbers, displaying the residual, and refusing to price any turn it cannot reconcile.

- **searchpack** — Turn your docs folder into a drop-in semantic search engine for your static site: a subsetted embedding table, a binary index and a 4 kB query shim, zip in hand, no backend ever. The situation: you run an Astro/Hugo/Docusaurus docs site on free static hosting, Algolia DocSearch declined your application, and you are not standing up a vector database for 300 pages; the query is "add semantic search to static site without backend". Tech: build-time embedding with `sentence-transformers/static-retrieval-mrl-en-v1` `model_int8.onnx` (31,259,319 B) through the STANDARD `@huggingface/transformers` 4.2.0 feature-extraction pipeline — it is a model2vec-style token→vector lookup table with no attention and no matmul, so it is fast single-threaded, and the standard pipeline avoids the exotic hand-built `input_ids` + int64 `offsets` call signature that `minishlab/potion-base-8M` (30,240,854 B) demands; keep potion as a documented alternate only. MRL-truncate to 256 dims, then the key move: subset the token→vector table to only the tokens that actually occur in your corpus (a docs site touches a few thousand of ~32k), typically 1–4 MB instead of 30, and int8-quantize it. Chunk vectors are emitted twice — 256-bit binary codes for a Hamming first pass (32× smaller) and int8 for rescoring. Parsing via `@mozilla/readability` 0.6.0 + `turndown` 7.2.4 for .html and a first-party heading splitter for .md; File System Access directory picker with a multi-file fallback; **fflate for the ZIP (stored mode) — `CompressionStream` does gzip/deflate/deflate-raw only and cannot write a ZIP container, which the original spec got wrong**. The shipped shim is hand-written and dependency-free: tokenize against the subsetted vocab → mean-pool → Hamming top-50 over a `Uint32Array` → int8 cosine rescore → top-10, with OOV tokens mapped to zero. Artefact: search.zip containing index.bin, vocab.bin, search.js (~4 kB) and a README with the copy-paste `<script>` snippet — the user leaves with a working search engine for their own website, and it is the only artefact in this list that then runs on a third party's machine. Privacy: your docs are parsed in the tab, and the shipped engine means your visitors' queries never reach anyone (Algolia sees every query typed into your logged-in internal docs). Displaces Algolia (DocSearch free tier is application-gated; paid plans price per 1,000 searches), Pinecone Builder $20/mo, Weaviate Serverless $45/mo minimum, turbopuffer Launch $16/mo minimum, or a serverless function calling OpenAI embeddings at a per-query cost that never stops. Ship `public/samples/docs-site.zip` (30 markdown pages of a fictional API reference). Hard part: the build-time embedder and the shipped shim must agree to cosine > 0.999 or the tool is emitting a broken index — DERIVE THE SHIM'S TOKENIZER FROM THE SAME SUBSETTED VOCAB STRUCTURE used at build time rather than reimplementing it, ship the self-test (re-embed 20 chunks with the shipped shim, assert cosine) as a visible green/red gate, and still emit the pack on failure clearly labelled "unverified" so a near-miss produces a diagnosable artefact rather than nothing.

- **scrubjay** — Scan a training or eval dataset for live-shaped API keys and PII before it leaves your machine, and get back a pseudonymised file plus an encrypted mapping that only you can reverse. The situation: you are about to upload 4 GB of support transcripts to a fine-tuning provider and you do not know what a customer pasted into chat two years ago; the query is "find api keys in jsonl dataset before upload". Tech: SHIP ~25 HIGH-PRECISION RECOGNISERS ONLY, per both feasibility reviews — the checksum-validated ones (Luhn for cards, mod-97 IBAN, US SSN structure, ABA routing) plus unambiguous provider prefixes (`AKIA[0-9A-Z]{16}` with its paired 40-char secret, `ghp_`/`github_pat_`, `sk-ant-api03-`, `sk-proj-`, `xox[baprs]-`, `sk_live_`, `AIza[0-9A-Za-z_-]{35}`, `hf_`, PEM `BEGIN … PRIVATE KEY` headers, `eyJ` JWTs, and the 32hex-usN Mailchimp shape) plus a Shannon-entropy gate at ≥3.5 bits/char over 20+ char tokens — not the 120-recogniser Presidio port, which is a week of precision tuning, not a day. Everything streams: `File.stream()` → `DecompressionStream('gzip')` → `TextDecoderStream` → a line-delimited parser across a `navigator.hardwareConcurrency` Worker pool, so a 4 GB `.jsonl.gz` never lands in memory (Workers need no cross-origin isolation, so this runs on GitHub Pages unmodified); `hyparquet` 1.27.1 (262 KB pure JS) for Parquet input rather than a 150 MB DuckDB bundle. Web Crypto does the load-bearing work: HMAC-SHA256 under a locally generated key produces stable pseudonyms (the same email is always `PERSON_0f3a`, so the data stays trainable), and AES-GCM-256 seals the mapping under a passphrase. CUT GLINER FROM V1 — `onnx-community/gliner_small-v2.1` `model_int8.onnx` is 183,403,734 B plus an 8,657,198 B tokenizer ≈ 192 MB, not the 174.9 MB claimed, and it is out of reach on a 4 GB phone. Artefact: dataset.clean.jsonl(.gz), findings.csv (record number, JSON path, rule, severity, 40-char context window), mapping.enc (AES-GCM-256 sealed, so the reversibility is not itself a liability), and the headline count "N live-shaped credentials and M PII spans in 4.1 GB". Privacy, stated plainly: uploading the file to a cloud scanner to learn whether the file contains secrets IS the disclosure — and the tool never verifies key liveness, because verifying means transmitting. Displaces Nightfall, Skyflow and Private AI, all of which sell this as enterprise DLP behind "contact sales"; Microsoft Presidio is MIT and free but is a Python package with no JavaScript port in existence. Ship `public/samples/support-transcripts.jsonl.gz` (2,000 synthetic rows with 14 planted secrets of known types and 30 deliberate near-misses). Hard part: false positives — base64 images, git SHAs, UUIDs and minified JS all trip an entropy detector — mitigated by the keyboard triage that dismisses an entire RULE CLASS in one keystroke rather than one row at a time, with the kill count and a random sample of what that class matched shown before you confirm.

- **chunkforge** — Drop a folder of PDFs and docs and watch a real query's retrieval ranks move as you drag the chunk-size slider, then export the chunks and the exact splitter config. The situation: your RAG assistant cites the wrong page and you cannot tell whether 512 tokens with 50 overlap or 1024 with 200 is the problem; the query is "best chunk size for rag" — one of the fattest keywords in the space, with Zilliz, Firecrawl, Unstructured, Databricks, Milvus, NVIDIA and IBM all fighting for it, and the free incumbent ChunkViz stopping exactly where the value starts. Tech: parsing entirely client-side with `pdfjs-dist` 6.2.108 text layer (per-item `transform` and `width` for column and heading inference), `mammoth` 1.12.0 for .docx, `@mozilla/readability` 0.6.0 + `turndown` 7.2.4 for .html; boundaries measured in REAL tokens via `@huggingface/tokenizers` 0.1.3 (~8.3 kB gz, zero deps) loading the target model's `tokenizer.json` from `huggingface.co/{repo}/resolve/main/` (CORS verified; ship the curated ungated-mirror registry because `meta-llama/*` and `google/gemma-*` 401 anonymously); embeddings from `sentence-transformers/static-retrieval-mrl-en-v1` `model_int8.onnx` (31,259,319 B) through the STANDARD `@huggingface/transformers` 4.2.0 pipeline — an EmbeddingBag with no attention, so re-embedding the whole corpus on every slider drag is genuinely sub-second, and note `model_q4` is 125,022,591 B because 4-bit does not compress an EmbeddingBag, making int8 the only shipping build; optional quality re-score with `Xenova/bge-small-en-v1.5` q8 (34,014,426 B); retrieval is first-party brute-force cosine over one `Float32Array` in a Worker; File System Access directory picker with a multi-file fallback. SHIP THREE STRATEGIES, NOT FIVE: fixed-token with overlap, recursive-separator, and markdown-heading-aware. Workflow: drop documents, type 2–5 queries you know are failing (no labelling chore — that is the whole point), drag the slider, watch each query's top-10 reorder live. Artefact: chunks.jsonl (id, text, source_file, page, char_span, token_count) for the winning strategy, a config snippet with the actual numbers filled in for LangChain `RecursiveCharacterTextSplitter` and LlamaIndex `SentenceSplitter` — the copy-paste line the user came for — and a per-strategy hit-rate table. Privacy: contracts, board packs and internal handbooks are parsed and embedded in the tab and never uploaded. Displaces LlamaParse $50/mo for 40k credits (~$0.003/page), Unstructured $0.03/page with a $3,000/mo cap, Reducto $0.015/credit and Chunkr $50/mo at $0.01/page. Ship `public/samples/handbook.pdf` (40-page employee handbook) with three example queries pre-filled. Hard part: keeping the slider interactive — TOKENIZE EACH DOCUMENT ONCE AND CACHE THE TOKEN-OFFSET ARRAY so every drag is pure array slicing plus re-embedding of cached spans; re-tokenizing per frame is 0.5–2 s on a 300-page corpus and will stutter badly. Also: do not present this as a PDF text extractor — six catalogue tools already live on that shelf; the product is the retrieval score.

- **epochcost** — Put an exact dollar figure on a multi-gigabyte fine-tuning or eval file, and hand back only the rows that break the context limit. The situation: you have a 1.2 GB JSONL, you are about to launch a fine-tune, and you need to know what an epoch costs and which rows will be silently truncated in the middle of an assistant turn (which trains the model to stop mid-sentence); the query is "openai fine tuning cost estimate jsonl". Tech: `gpt-tokenizer` 3.4.0's per-encoding standalone browser builds, lazy-loaded one at a time — o200k_base 2.05 MB for GPT-4o/5-class, o200k_harmony for gpt-oss, cl100k_base 2.05 MB, p50k_base 503 KB — for exact OpenAI counts, and `@huggingface/tokenizers` 0.1.3 (8.3 kB gz, `tokenizer.json` fetched over CORS) for exact Qwen/Mistral/Llama/DeepSeek counts; Claude is labelled ESTIMATE in the UI with the reason stated (no public local tokenizer since Claude 3; tiktoken undercounts by 15–20% on prose and far more on code). Ingestion is fully streaming — `File.stream()` → `DecompressionStream('gzip')` → `TextDecoderStream` → NDJSON splitter → round-robin across a `navigator.hardwareConcurrency` Worker pool with transferable `ArrayBuffer` chunks, explicit backpressure and correct handling of records straddling a chunk boundary — so a 4 GB file never materialises; `hyparquet` 1.27.1 (262 KB) reads Parquet without a 150 MB DuckDB bundle, keeping it usable on a phone; histograms accumulate streamingly and render on OffscreenCanvas; the price table is a dated, user-editable JSON so it can be corrected rather than quietly wrong. Artefact: token-stats.csv (per-record counts by role), a histogram PNG, under-limit.sorted.jsonl (length-bucketed and ready for packed batching) and over-limit.jsonl containing only the rows you have to fix — a work queue, not a statistic — headlined by total training tokens, cost per epoch in dollars, and "you are wasting N% of your training tokens on padding". Privacy: the file never leaves the machine; the only network fetch is a public tokenizer. Displaces W&B Weave, which charges $0.10/MB ($100/GB) to ingest the same JSON, Braintrust Pro at $249/mo, and LangSmith Plus at $39/seat/mo; the free single-textarea counters cannot take a file, cannot do distributions and cannot see truncation. Ship `public/samples/finetune-train.jsonl.gz` (5,000 chat rows, ~40 of them over any sane limit, with visible padding waste). Hard part is scope discipline and throughput: DRAW A HARD LINE AGAINST CHATPRINT — input is a FILE only, with no chat-template rendering, no per-prompt inspector and no messages paste box — and on a 4-core phone a multi-GB file is 5–10 minutes with real tab-kill risk, so measure MB/s over the first 20 MB, show an honest ETA before committing, and keep a resumable chunk offset so a killed tab does not lose the run.

The situation: you have 1,400 photos of a person, a product or a style, half of them near-identical burst frames and a few badly blurred, and your alternative is renting Colab to run a Python script you do not understand; the query is "remove duplicate images from lora training dataset".
